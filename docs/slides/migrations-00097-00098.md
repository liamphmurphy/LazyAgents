# Slides migrations 00097 and 00098: deploying and rolling back

These migrations ship with the Slides epic (LAZYAGENTS-103 and LAZYAGENTS-104). Nothing here has been applied to production. These are the steps for whoever deploys it.

| Migration | What it does |
| --- | --- |
| `00097_slides.sql` | Allows `deck` in `chat_canvases.kind` and `slides` in `chat_spaces.app`. Adds `deck_assets`, the deck image rows. |
| `00098_slides_blob_sweep.sql` | Adds `deck_blob_sweep`, the queue of released image keys, and the `deck_assets_queue_blob` trigger that fills it. |

Both are additive on the way up. Existing rows aren't rewritten. The only locks are brief `ALTER TABLE … CONSTRAINT` locks on `chat_canvases` and `chat_spaces`, plus a validation scan of those tables, which takes seconds at our size.

## Deploy

The API and the runner apply pending migrations when they start (`db.Migrate`, serialised by an advisory lock). To apply them on their own before rolling out, run the new binary's migrate command with production's `DATABASE_URL`:

```sh
# 1. Back up first (see below).
# 2. With the new image or binary:
DATABASE_URL=… vesper migrate
# 3. Then roll out the API and the runner as usual.
```

Roll out the runner along with the API. The image sweep runs in the runner. Until the new runner is up, released image keys just wait in `deck_blob_sweep`.

## Backup

Take a normal logical backup just before migrating, for example:

```sh
pg_dump --format=custom --file=vesper-pre-slides-$(date +%Y%m%d%H%M).dump "$DATABASE_URL"
```

The up migrations lose nothing, so the backup is only for the lossy rollback below. Once people have made decks, restoring this backup would also lose everything else written after it. Prefer the rollback below to a restore.

## Roll back

Roll back with the previous release's binary, after stopping the new API and runner:

```sh
go run github.com/pressly/goose/v3/cmd/goose@v3.29.0 -dir server/migrations postgres "$DATABASE_URL" down-to 96
```

**This is lossy by design.**

- **00098 down:** drops the sweep queue and its trigger. Keys still queued are forgotten, so their blobs stay in object storage.
- **00097 down:** deletes every deck, its versions and image rows, every chat in a Slides space with that chat's messages and runs, and the Slides spaces. It then restores the old CHECK constraints.

**What survives:**

- Image blobs under `slides/` in the artifact bucket. Nothing references them after a rollback; they can be removed by prefix if wanted.
- Docs, mockups and ordinary chats.

To keep the decks, export them as PDF or PPTX first, or keep the backup.

## Checklist after deploying

1. `SELECT max(version_id) FROM goose_db_version WHERE is_applied;` returns `98`.
2. `\d deck_assets` and `\d deck_blob_sweep` exist, and `SELECT tgname FROM pg_trigger WHERE tgname = 'deck_assets_queue_blob';` returns one row.
3. In the app:
   - create a deck from Apps → Slides, add an image, duplicate the deck, and delete the original;
   - the copy still shows the image.
4. `SELECT count(*) FROM deck_blob_sweep;` is 0 again within about an hour and a minute of the delete. The copy keeps the key, so the sweep only dequeues it. Delete the copy too; after the next sweep, the object `slides/{workspace}/{user}/{sha256}` is gone from the artifact bucket.
5. The runner's logs show no repeated `sweep deck blobs` warnings.

## How this was validated (LAZYAGENTS-104)

All of this ran against disposable databases. No shared environment was touched.

- **Migrating a fresh database:**
  - `vesper migrate` brought a new Postgres 17 database to version 98, and the tables and the trigger were present.
  - goose v3.29.0 `down-to 96` then ran 00098 down and 00097 down. The tables were gone and the old constraints back: `kind IN ('text','svg')` and `app IN ('finance','docs')`.
  - `vesper migrate` brought the database back to 98.
- **Rolling back with data in place:** `TestSlidesMigrationsRollBackAndReapply` rolls back a database holding:
  - decks, a copy, an image, a persona run on a deck's chat, and a document.
  - Only the Slides data is lost. The document stays.
  - The migrations apply again afterwards, and the trigger queues keys again.
